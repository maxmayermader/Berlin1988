## Phase Goal

> **Goal (verbatim from ROADMAP.md Phase 3):** A real group can find each other without trading
> codes, the host controls the room, everyone can talk, and one person dropping does not kill the
> match.
>
> **MVP_MODE note:** the ROADMAP `**Goal:**` line is not in user-story format; per the MVP-mode
> contract no story was invented here. See 03-01-PLAN.md's identical note.

**This plan's slice:** the host actually owns the room — they size it and they can remove someone,
and everyone sees it happen at once.

<objective>
Deliver LOBBY-01 and LOBBY-02: a host-only seat-count control spanning 1-4 (D-04) that refuses to
drop below the occupied seats (D-05), and a host-only kick that ejects a player with a `KICKED`
message, a home-page banner, and an open door back in via the join code (D-06).

This is the first host-authority surface in the codebase. No host-only message handler exists in
Phase 1 or Phase 2 — `apps/party/CLAUDE.md` rule 5 states the rule ("host-only messages are
verified against the seat that owns the room, not against a flag in the message body") but nothing
has needed it until now. The pattern this plan establishes is the one every later host-only message
will copy.

Purpose: LOBBY-01, LOBBY-02 (D-04, D-05, D-06).
Output: `SET_SEAT_COUNT`/`SET_SEAT_COUNT_REJECTED` and `KICK`/`KICKED` wire messages,
`setSeatCount`/`canSetSeatCount`/`vacateSeat` in `state.ts`, `handleSetSeatCount`/`handleKick` in
`handlers.ts`, a `SeatCountControl` and per-row Kick button in the lobby, and a dismissible removal
banner on the home page.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| any seated client → match room (`SET_SEAT_COUNT`) | The first host-only message in the codebase; every seated player can send it |
| any seated client → match room (`KICK`) | A message that removes another player from the room |
| match room → the kicked connection (`KICKED`) | A targeted send to one connection rather than a room-wide fan-out |
| kicked browser → match room (rejoin `JOIN`) | An intentionally open door (D-06), not a bypass |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-06 | Elevation of Privilege | `handleSetSeatCount`, `handleKick` | high | mitigate | Both resolve the acting seat via `seatFor(state, connectionId)` and compare `seat.playerId` against `state.hostPlayerId` before any mutation. Neither message schema has a field that could carry a claimed role, and the client-side `isHost` derivation is explicitly commented as UX-only. Tests: the non-host rejection cases in Task 1 and Task 2's acceptance criteria. |
| T-03-07 | Spoofing | `KICK` target selection | high | mitigate | `KICK` carries a seat index bounded 0..3 by the wire schema, not a playerId a client could substitute. The handler additionally refuses an index outside the *current* `state.seats` bounds (which shrinks with the seat count), an `OPEN` target, and the host's own index. Test: the four rejection cases in Task 2. |
| T-03-08 | Tampering | `SET_SEAT_COUNT` below the occupied threshold | high | mitigate | `canSetSeatCount` is the single server-side authority and uses the highest occupied seat *index* rather than the occupied *count*, closing the gap case a prior kick creates. The greyed client option is a mirror, never the enforcement. Test: the seats-0-and-2-occupied case in Task 1. |
| T-03-09 | Denial of Service | host kicking its own seat, orphaning the room | high | mitigate | `handleKick` refuses `seatIndex` equal to the host's own seat index. Without this, a host could vacate `hostPlayerId`'s seat and leave a room in which no connection can ever pass the host check again — an unrecoverable lobby. Test: the self-kick rejection case in Task 2. |
| T-03-10 | Spoofing | kicked player rejoining with the same code | low | accept | D-06 locks this as intended behaviour: no per-room ban or kick list is built this phase, and a kicked player is explicitly free to rejoin. 03-RESEARCH.md's Security Domain records this as "a deliberate, locked, non-security requirement, not a vulnerability". |
| T-03-11 | Information Disclosure | `KICKED` targeted send | medium | mitigate | The `KICKED` payload carries only a fixed human-readable reason string — no seat index, no other player's identity, no room state. It goes through `sendTo`, which runs `serverMessageSchema.parse` before serialising, so the payload cannot be widened without a schema change. |
| T-03-12 | Repudiation | no audit trail of who kicked whom | low | accept | A no-accounts private lobby among friends has no durable identity to attribute a kick to, and the room's own state is ephemeral. Out of scope at ASVS L1 for this milestone. |
