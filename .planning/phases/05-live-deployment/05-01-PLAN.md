<objective>
Make this repository produce a Vercel-shaped production build, and build the two tools that can
prove any deployed URL is actually wired to the production PartyKit server.

Purpose: every known risk in this phase is a build risk (`05-RESEARCH.md` Pitfalls 1, 2, 4) and
every acceptance criterion is an external observation of a deployed site. Both are cheaper to
retire here, before a human touches the Vercel dashboard, than after.

Output: `transpilePackages` and a bounded Node pin in the repo; a re-runnable `pnpm smoke:deploy`
script; and a Playwright config that can point the existing two-browser create-and-join spec at a
deployed URL instead of localhost.
</objective>

<assumption_delta_decision>
The deterministic detector fired for this phase (`pluralization`, on the connective "also" in the
ROADMAP risk sentence). The literal signal is a false positive — "also" there joins items in a risk
list, not a second instance of a noun. But re-reading the phase scope for the underlying question
surfaces a real transition that the signal happened to land next to, so it is recorded rather than
dismissed.

- **Noun now primary:** *deployment* — an environment-scoped build at its own URL — rather than
  *the site*, a single implied thing. D-01 gives every branch a public preview URL, so from this
  phase onward there are always several live deployments of `apps/web` at once.
- **Decision:** `promote`. The plans treat "a deployment" as the primary unit throughout:
  `NEXT_PUBLIC_PARTYKIT_HOST` is configured per Vercel environment rather than once (05-03),
  `pnpm smoke:deploy` takes the target URL as an argument and hardcodes no host (05-01 Task 2),
  `playwright.config.ts` takes its base URL from the environment (05-01 Task 3), and
  `/deploy-stamp` exists so any one deployment can be told from another (05-04). Nothing in this
  phase assumes there is exactly one.
- **Rationale for promote over add-alongside:** the generalization is already true the moment the
  Vercel project exists — previews are on by default and D-01 accepted them deliberately. Treating
  production as the real case and previews as an exception would mean a second code path for
  preview URLs, which is precisely the shape this taxonomy exists to prevent.

Advisory only: this record informs the plan and blocks nothing.
</assumption_delta_decision>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| repository → build container | Everything in this repo is executed by Vercel's build container under the maintainer's account; a change here is a change to what runs there |
| build output → public internet | `NEXT_PUBLIC_*` values are inlined into the client bundle this build emits and are readable by anyone who loads the page |
| operator environment → test runner | `PLAYWRIGHT_BASE_URL` newly controls which origin a browser test drives |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-01 | Information Disclosure | `NEXT_PUBLIC_*` build-time inlining (`apps/web/lib/socket.ts` → client bundle) | medium | mitigate | This phase introduces exactly one such variable and its value is a public hostname. Task 1's acceptance criteria assert no `scripts` entry and no new environment coupling is added here, and plan 05-03 Task 1 forbids adding any Vercel variable other than `NEXT_PUBLIC_PARTYKIT_HOST`. A secret must never be given a `NEXT_PUBLIC_` name — by definition it would ship to every visitor. |
| T-05-SC | Tampering | package-manager supply chain (`pnpm-lock.yaml`) | high | mitigate | No package is installed in any workspace this phase (`05-RESEARCH.md` Package Legitimacy Audit: not applicable).
