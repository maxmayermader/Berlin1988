## Phase Goal

**As a** group of players, **I want to** go from the home page through a lobby into a complete 14-round match and see a result, **so that** we can actually play Berlin 1988 in a browser.

This plan delivers the third vertical slice: *orders go in sealed, the clock runs the round, and the round resolves*.

<objective>
Turn the freshly-created `GameState` from Plan 01-02 into a running round loop inside the room: `SUBMIT_ORDER` validated by the engine and held secret, a per-seat commit count on the wire, a server-authoritative 90-second deadline with auto-Hold, bot seats playing through the identical submit path, and `resolveRound()` firing exactly once per round with a per-connection projected view going back out.

Purpose: this is the highest-risk work in Phase 1 and the reason it is pulled forward. Two of the five ROADMAP.md research flags land here — wire-level fog of war (`apps/party/tests/fog-wire.test.ts`, named in 01-VALIDATION.md as the highest-priority new test in the phase) and PartyKit hibernation across the 90-second order window. `PlayerView` being type-safe is not the same as wire-safe, and the naive implementation of `ROUND_RESOLVED { log, view }` ships the unfiltered resolution log to everyone.

Output: a room that plays rounds by itself. A solo host against three bots reaches round 2, then round 3, then the round limit, with every byte on the wire produced per-recipient by `projectView()`.
</objective>

**`packages/shared/src/protocol.ts` — the order slice of the wire contract.**
Declare `actionSchema` as a `z.discriminatedUnion('type', [...])` with one member per `Action` variant, annotated `const actionSchema: z.ZodType<Action>` so a future divergence between the schema and `packages/shared/src/orders.ts` is a compile error rather than a runtime surprise. Node and card ids arrive as `z.string()` and are branded on the way in; the engine re-checks membership anyway.
Declare `agentOrderSchema` = `{ agentId: z.string(), actions: z.array(actionSchema).min(1).max(2), buySilencers: z.number().int().min(0).optional() }`. Two is the hard ceiling because an agent has exactly two actions per round; the engine rejects a third with `TOO_MANY_ACTIONS`, and the schema refusing it first means an oversized payload never reaches the engine at all.
Add to `clientMessageSchema`: `{ type: 'SUBMIT_ORDER', round: z.number().int(), agentId: z.string(), actions: z.array(actionSchema).min(1).max(2), buySilencers: z.number().int().min(0).optional() }`. The message carries no `playerId` — the acting seat is resolved from the connection binding, as with `SET_READY`.
Add to `serverMessageSchema`:
`{ type: 'ORDER_ACK', round: number, agentId: string }`,
`{ type: 'ORDER_REJECTED', round: number, agentId: string, code: <the eight OrderRejection codes as a z.enum>, message: string }`,
`{ type: 'OPPONENT_COMMITTED', playerId: string, agentsCommitted: number, agentsTotal: number }`,
`{ type: 'ROUND_RESOLVED', view: z.custom<PlayerView>() }`.
`ROUND_RESOLVED` has exactly one payload field. `PlayerView.lastRound` is the log, already filtered to that recipient's entitlement by `projectView`; adding a second field for the pipeline's own return value would put the unredacted array on the wire. **`apps/party/src/handlers.ts` — `handleSubmitOrder`.**
Resolve the acting seat with `seatFor(state, connection.id)`; no binding means return without touching state. Reject with `ERROR { code: 'WRONG_PHASE' }` unless `RoomState.phase === 'IN_GAME'` and `gameState.phase === 'ORDERS'`. Reject when the message's `round` differs from `gameState.round` — a stale frame from a client that has not yet processed a resolution must not land in the new round.
Then call `submitOrder(gameState, seat.playerId, { agentId, actions, buySilencers })` and branch on its `rejection` field exactly as the engine returns it: `null` means store the returned state and reply `ORDER_ACK`; non-null means leave state untouched and reply `ORDER_REJECTED` with the engine's own `code` and `message`. Never synthesise a rejection message locally and never answer before `submitOrder` returns — RESEARCH.md Pitfall 2/2b is that a player believes an order landed when it did not, and an ack sent optimistically is exactly that bug.
Ownership is enforced twice on purpose: the acting `PlayerId` comes from the connection binding, and the engine independently answers `NOT_YOUR_AGENT` for an agent that is not on that seat.
After a successful submit, call `sendCommitted` for the acting seat and then `shouldCloseRound`.

**`apps/party/src/broadcast.ts` — extend the chokepoint.**
`sendCommitted(room, state, playerId)` builds `{ type: 'OPPONENT_COMMITTED', playerId, agentsCommitted, agentsTotal }` where `agentsCommitted` is the number of that seat's live agents whose id is a key of `gameState.pendingOrders`, and `agentsTotal` is that seat's live agent count. The count is computed from key presence alone — the order object at that key is never read, indexed, spread, or serialised anywhere in this function. This frame is identical for every recipient and carries no field capable of holding an `Action`, which is why room-wide fan-out is permitted for it (SKELETON.md's fog-boundary row names commit counts explicitly).
`sendResolved(room, gameState)` iterates `room.getConnections()`, resolves each connection's seat via `seatFor`, computes `projectView(gameState, playerId)` for that one recipient, and transmits `{ type: 'ROUND_RESOLVED', view }` to that connection alone. The `log` returned by `resolveRound` is not a parameter of this function and is not in scope inside it.

**`apps/party/src/round.ts` — new, flat, single-purpose (consistent with `apps/party/src/CLAUDE.md`'s file table).**
`shouldCloseRound(state: RoomState): boolean` returns `state.phase === 'IN_GAME' && state.gameState !== null && allCommitted(state.gameState)`.
`closeRound(state: RoomState, reason: 'ALL_COMMITTED' | 'DEADLINE'): RoomState` is the only place `resolveRound` is called in the entire repo outside `packages/`. It returns `state` unchanged unless the room is `IN_GAME` with a non-null `gameState` whose `phase` is `'ORDERS'` — that guard is what makes a double-fired alarm, a duplicated message, or a late submission landing mid-close a no-op rather than a second resolution of the same round. On `'DEADLINE'` it first applies `autoHoldMissing`. It then calls `resolveRound`, keeps only the returned `state`, and when that state's `outcome` is non-null sets `RoomState.phase = 'ENDED'`. Persist to room storage before returning.

**`apps/party/src/timers.ts` — new.** Export `scheduleRoundDeadline(state: RoomState, now: number): RoomState`, `onRoundAlarm(state: RoomState, now: number): RoomState`, and `botDelayMs(rng: RngState): number`.
`scheduleRoundDeadline` computes `now + state.gameState.settings.roundTimerSeconds * 1000` and stores it on `RoomState` alongside the round number it belongs to (`deadlineAt` and `deadlineRound`). If `deadlineRound` already equals the current `gameState.round`, it returns the state untouched — the guard is what stops a late join, a codename change, or a re-broadcast from silently extending or restarting a running countdown, which would make the visible timer jump backwards.
`onRoundAlarm` delegates to `closeRound(state, 'DEADLINE')` and then, if the resulting room is still `IN_GAME`, schedules the next round's deadline. If the resulting room is `ENDED` it schedules nothing.
`botDelayMs` draws from the engine's seeded RNG: `1500 + nextInt(rng, 2501)`. The padding range is `docs/ARCHITECTURE.md` §7's existing tuning target, not a new number.
