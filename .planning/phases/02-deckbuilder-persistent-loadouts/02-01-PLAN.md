## Phase Goal

**As a** player, **I want to** build and keep my own 10-card loadout and take it into a match, **so that** I play my own deck instead of the default the skeleton shipped with.

This plan delivers the first vertical slice, and it is the phase's tracer: *the deck I picked is the deck I play*. One preset click on `/deck`, persisted with no login, carried into the room, dealt to my agent at match start.

<objective>
Cut the whole pipe, end to end, on the thinnest possible path: a player follows a link from the home page to `/deck`, loads one of the four starter presets, and the match they then play deals their agent that loadout instead of the hardcoded Phantom every seat gets today.

Purpose: `02-RESEARCH.md` Pitfall 3 is the one that sinks this phase — `SUBMIT_LOADOUT` is documented in `docs/ARCHITECTURE.md` §5 but has never been implemented, so a plan that treats "persist to localStorage" as the whole of DECK-04 ships a deckbuilder that works perfectly and a match that ignores it. Four separate layers have to move in one connected piece — the wire schema, the room handler, the `RoomSeat` field, and `startMatch` — and proving them together on the agent's best early-context tokens is cheaper than discovering the seam after the card grid and the legality meter are already committed on top of it.

Output: a working `/deck` route, the `SUBMIT_LOADOUT` / `LOADOUT_ACK` / `LOADOUT_REJECTED` wire messages, a seat-scoped room handler, per-seat loadouts at match start, and two tests that meet in the middle — a Playwright spec proving the browser half up to the frame it sends, and a Vitest room integration proving that frame becomes `GameState.players[x].loadout`.
</objective>

export function loadIdentity(storage: StorageLike | null = browserStorage()): Identity {
  if (storage) {
    const raw = storage.getItem(STORAGE_KEY);

**`packages/shared/src/protocol.ts` — three new members, no new file.** Add one `clientMessageSchema` union member `{ type: z.literal('SUBMIT_LOADOUT'), cards: z.array(cardIdOnWire).max(64) }`, reusing the `cardIdOnWire` transform already defined in this file. It carries no identity or seat-index field at all; extend the existing comment block that explains why the other inbound messages carry none. The `.max(64)` bound exists so an oversized array is rejected by Zod before any engine call touches it (T-2-05) — it is deliberately looser than the ruleset's ten so an over-long deck still reaches `validateLoadout` and gets a real `WRONG_SIZE` message back rather than a generic malformed-frame error. Add two `serverMessageSchema` members modelled on `ORDER_ACK`/`ORDER_REJECTED`: `{ type: z.literal('LOADOUT_ACK'), cards: z.array(z.string()) }` echoing what the room stored, and `{ type: z.literal('LOADOUT_REJECTED'), message: z.string() }` carrying the joined engine violation text.

**`apps/party/src/state.ts` — one field, one reducer.** Add `loadout: CardId[] | null` to `RoomSeat` with a comment stating it is server-only and must never enter `toSnapshot()`. Initialize it to `null` in `emptySeats()`. Add `setLoadout(state, playerId, cards): RoomState` mapping over `seats` and replacing only the matching seat, immutably, exactly like `setReady`. Two deliberate differences from `setCodename`: the guard admits both `LOBBY` and `LOADOUT` phases (matching `startMatch`'s own guard) and returns `state` unchanged in any other phase (T-2-07), and it does **not** refuse a seat whose `ready` flag is set — D-05 clears ready as a separate explicit step from the client, so gating the write on ready here would silently drop a legitimate submission. Leave `toSnapshot()` untouched; its six-field seat projection is what keeps the new field off the wire.

**`apps/party/src/handlers.ts` — `handleSubmitLoadout`.** Export `interface SubmitLoadoutResult { state: RoomState | null; toSender: ServerMessage | null }`. The handler takes `(state, message: Extract<ClientMessage, { type: 'SUBMIT_LOADOUT' }>, connectionId)` and, in order: returns the null-state result if there is no state; resolves the acting seat with `seatFor(state, connectionId)` and returns silently on an unbound connection, exactly as `handleSetReady` does; returns a `WRONG_PHASE` `ERROR` frame if the room has already left `LOBBY`/`LOADOUT`; calls `validateLoadout(message.cards, DEFAULT_RULESET)` and, on a non-empty result, returns `{ state, toSender: { type: 'LOADOUT_REJECTED', message: violations.map((v) =&gt; v.message).join(' ') } }` with state untouched; otherwise returns the state produced by `setLoadout` plus a `LOADOUT_ACK` echoing the accepted cards. The engine call is the authority — the client's disable-until-legal behavior from D-03 is a convenience for the player and is never the enforcement (T-2-02). Never read a seat or player identifier from the message body; the schema has no such field to read (T-2-01).

**`apps/party/src/room.ts` — an explicit branch.** Add `if (message.type === 'SUBMIT_LOADOUT') { ... return; }` *above* the file's final unguarded block. Without it, the new message falls straight into `handleSubmitOrder` and is misinterpreted. Persist the returned state and `sendTo(sender, result.toSender)` when non-null. Do **not** call `sendLobby` here: the public snapshot is unchanged by a loadout write, and broadcasting one would be the exact leak T-2-03 guards against. Do not call `syncAlarm` either — no timer changed.

**`apps/party/src/settings.ts` — per-seat loadouts at match start.** Replace the blanket-overwrite loop with a per-entry branch. Build a lookup from the `filled` seats keyed by `playerId`. For each `gameState.players` entry: if the matching seat is missing or `seat.kind === 'BOT'`, leave that player's entry exactly as `createMatch` built it, so a bot keeps the per-faction starter loadout `defaultLoadoutFor` gave it (02-RESEARCH.md Pitfall 4 — a bot seat has no submitted deck and routing it through the human path either crashes or hands every bot an identical human-authored deck). For a non-bot seat, use `seat.loadout` when it is non-null *and* `validateLoadout(seat.loadout, DEFAULT_RULESET)` returns empty; otherwise fall back to `[...PHANTOM]`.
