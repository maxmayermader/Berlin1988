## Phase Goal

**As a** player, **I want to** build and keep my own 10-card loadout and take it into a match, **so that** I play my own deck instead of the default the skeleton shipped with.

This plan hardens the room half of that promise: *the deck the match deals me is mine, is legal, and is nobody else's business*.

<objective>
Prove the room's side of the loadout contract against the cases a real client will never send: a frame from a connection bound to a different seat, a deck that breaks each of the five legality rules, an oversized payload, a submission after the match has already started, and a stored deck that stopped validating between submission and match start. Then prove the fog claim on literal wire frames rather than by inspection.

Purpose: D-03 makes the client refuse to offer Save until the deck is legal, which means the *only* way an illegal loadout reaches the room is a buggy or hostile client — precisely the path no manual testing exercises. `apps/party/src/CLAUDE.md` rule 2 and this repo's whole seat-token design exist because a `playerId` in a message body is a spoofing surface, and `SUBMIT_LOADOUT` is the first new inbound message the room has accepted since that rule was written. 02-RESEARCH.md Pitfall 4 adds the failure that has nothing to do with attackers: `startMatch`'s loop never distinguished seat kinds, so the naive per-seat fix either crashes a bot seat or hands every bot an identical human-authored deck.

Output: `apps/party/tests/loadout.test.ts` grown from the tracer's single happy path into the room's full contract, plus whatever hardening those cases drive into `handlers.ts`, `state.ts` and `settings.ts`.
</objective>


**Bot seat construction** (`apps/party/src/bots.ts`) — `fillEmptySeatsWithBots` runs only inside `startMatch` and gives each open seat a `playerId` of `bot-{index}-{personality}`, `kind: 'BOT'`, `ready: true`. **Faction defaults** (`packages/engine/src/createMatch.ts:126-137`) — what a bot seat must keep:

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → PartyKit room (`SUBMIT_LOADOUT`) | The phase's real trust boundary. The client's legality gate is convenience; this is enforcement. |
| connection id → seat | Every inbound message's authority. A `playerId` in a body would bypass the whole seat-token design. |
| `RoomSeat.loadout` → `GameState.players[x].loadout` | Server-internal, but a bad value here corrupts a live match rather than a form. |
| `RoomState` → `ROOM_STATE` broadcast | The fog boundary, asserted here on literal frames rather than by inspection. |

<planner_assumptions>
Flagged for the record — surfaced, not dropped.

- **`setLoadout` deliberately does not inherit `setCodename`'s rename-before-ready rule.** `setCodename` refuses a seat that has already readied; `setLoadout` accepts one. D-05 clears ready as an explicit, separate step from the client, so a guard here would silently drop a legitimate save from a player who readied first and then edited — and silence is the worst possible answer to a save the player believes succeeded. 02-PATTERNS.md calls for exactly this difference.
- **The wire bound and the rules bound are intentionally different numbers.** The schema caps `cards` at 64 to keep an absurd payload away from the engine, while the ruleset's `loadoutSize` is 10. Anything between the two parses and gets a real `WRONG_SIZE` message rather than a generic malformed-frame error, which is the difference between a buggy client that can be fixed and one that can only be guessed at.
- **This plan may make small fixes in `handlers.ts`, `state.ts` and `settings.ts` but adds no new surface.** The wire schema and `room.ts`'s routing belong to Plan 02-01; anything wrong there is a defect to fix in place, not a redesign to attempt here.
</planner_assumptions>
