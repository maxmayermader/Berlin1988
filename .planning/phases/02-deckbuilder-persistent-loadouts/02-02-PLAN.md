## Phase Goal

**As a** player, **I want to** build and keep my own 10-card loadout and take it into a match, **so that** I play my own deck instead of the default the skeleton shipped with.

This plan delivers the second vertical slice: *build the deck card by card, and see the rules while you do it, not after*.

<objective>
Turn the tracer's preset-only shell into a real deckbuilder: the whole 34-card pool, browsable and grouped the way `docs/GAME_DESIGN.md` §6.2 already tables it, with a per-card Add/Remove toggle and a persistent readout that answers "is this legal, and if not, why" on every single change.

Purpose: DECK-02's whole point is that legality is a *live instrument*, not a submit-time verdict — a player builds toward 10 cards, 26 Budget Points, three-per-icon and two colors by watching those four numbers move, and a deckbuilder that only reports at submit makes the constraint space invisible. The one way to get this wrong is to compute the answer twice: 02-RESEARCH.md Pitfall 2 is a client-side calculator that agrees with the engine almost always, and the "almost" is a save button that is enabled while the room rejects the payload.

Output: `CardGrid`, `LegalityMeter`, a widened `Deckbuilder`, and one pure `loadoutLegality` derivation that calls `validateLoadout` and `budgetPointsOf` and computes no rule of its own.
</objective>

**The card pool, exactly as it exists** (`packages/engine/src/content/cards.ts`) — 24 actives (six icons × four sectors) plus 10 passives, 34 total. A fixed, known size: no pagination, no virtualization.
```typescript
export const ACTIVE_CARDS: readonly ActiveCard[];   // 24
export const PASSIVE_CARDS: readonly PassiveCard[]; // 10
export const ALL_CARDS: readonly Card[] = [...ACTIVE_CARDS, ...PASSIVE_CARDS];
export function getCard(id: CardId): Card;          // throws on unknown
export function tryGetCard(id: CardId): Card | undefined;  // undefined on unknown
export function isActive(c: Card): c is ActiveCard;
export function isPassive(c: Card): c is PassiveCard;
```
Representative rows, to show the field shapes the tiles render:
```typescript
active('wt_blue', 'CIA Signals Net', 'WIRETAP', 'BLUE', 2, 1, 3,
       'Scan a node. In a BLUE sector, also scans every adjacent node.')
//     id       name                icon      sector  intelCost cooldown budgetPoints text

        'On a neutral contested node, +25% to win the roll.')
```

Note that a **passive still carries an `icon`** and `packages/shared/src/cards.ts:39` states passives count against the per-icon maximum — so a passive tile must show its icon even though it lives in the Passives section, or the icon pips become unexplainable.

**The canonical section order** (`packages/shared/src/enums.ts`) — the one place this order is declared:
```typescript
export type IconType = 'AGENT' | 'WIRETAP' | 'BRIBE' | 'DECOY' | 'SAFEHOUSE' | 'STRIKE';
export const ICONS: readonly IconType[] = ['AGENT','WIRETAP','BRIBE','DECOY','SAFEHOUSE','STRIKE'] as const;
export type Sector = 'RED' | 'BLUE' | 'GOLD' | 'GREEN';
export const SECTORS: readonly Sector[] = ['RED','BLUE','GOLD','GREEN'] as const;
```
This canonical order differs from the informal listing in 02-CONTEXT.md's D-04 prose ("Decoy, Wiretap, Strike, Bribe, Safehouse, Agent"). Neither ordering is normatively locked by a decision, and 02-RESEARCH.md and 02-UI-SPEC.md both resolve it the same way: use the single canonical `ICONS` array so there is never a second, hand-maintained order to drift.

**The legality primitives** (`packages/engine/src/loadout.ts`, read in full — this is the whole file's logic):
```typescript
export function validateLoadout(loadout: Loadout, ruleset: Ruleset): LoadoutViolation[] {
  // WRONG_SIZE when loadout.length !== ruleset.loadoutSize
  // UNKNOWN_CARD per id tryGetCard() cannot resolve
  // ICON_LIMIT per icon whose count exceeds ruleset.maxPerIcon
  // TOO_FEW_COLORS when the distinct sector count is below ruleset.minColors
  // OVER_BUDGET when summed budgetPoints exceeds ruleset.maxBudgetPoints
}
export function budgetPointsOf(loadout: Loadout): number;
```
It aggregates through a `Map` keyed by icon and a `Set` of sectors, so the result is **order-independent** and there is **no duplicate-id rule of any kind** — `Loadout` is a plain array and id uniqueness is never checked. Messages are already human-readable, e.g. `At most 3 WIRETAP cards allowed, got 4.` and `Loadout costs 27 Budget Points, limit is 26.`

**The ruleset the client validates against** (`packages/engine/src/content/rulesets.ts`) — `DEFAULT_RULESET` with `loadoutSize: 10, maxPerIcon: 3, minColors: 2, maxBudgetPoints: 26`. `apps/party/src/settings.ts:36` hardcodes `rulesetId: 'default'` for every match this phase, so importing `DEFAULT_RULESET` directly on the client cannot validate against the wrong ruleset (02-RESEARCH.md Open Question 3).

**`apps/web/lib/loadoutStore.ts` — two actions and one pure derivation.** Add `add(cardId)` (appends to the end of the draft array) and `remove(cardId)` (drops the first entry matching that id), each persisting through the same `saveLoadout` path `loadPreset` already uses so the save-failure status keeps working unchanged. Export a pure `loadoutLegality(loadout: readonly CardId[]): LoadoutLegality` that calls `validateLoadout(loadout, DEFAULT_RULESET)` and `budgetPointsOf(loadout)` and assembles everything the meter renders: `violations`, `budgetPoints`, `cardCount`, `iconCounts` (a count per entry of `ICONS`, present even at zero), `colorsPresent` (a set or record over `SECTORS`), and `isLegal` derived solely from `violations.length === 0`. It computes **no rule of its own** — `isLegal` is never assembled from the individual counts, because two independent answers to "is this legal" is exactly the drift 02-RESEARCH.md Pitfall 2 describes. Keep it a plain exported function rather than store state or a hook: it is pure, it must be callable from a test with no React, and stale derived state in Zustand is how a "live" meter stops being live.

**`apps/web/components/deck/CardGrid.tsx`.** Props `{ cards: readonly Card[]; loadout: readonly CardId[]; onAdd: (id: CardId) =&gt; void; onRemove: (id: CardId) =&gt; void }`. Render one section per entry of the canonical `ICONS` array containing that icon's active cards, then a final `Passives` section containing every passive — seven sections, 34 tiles, matching D-04 and 02-UI-SPEC.md's `populated` row. Derive the sections by filtering the `cards` prop, never from a hand-written list, so a card added to the engine appears here with no edit.

Each tile carries `data-card-id={card.id}` and shows: name (Label weight), sector swatch **plus its uppercase text label**, icon name, Budget Point cost, the card's `text`, and — for a passive — a `Consumable` or `Permanent` tag at Label size. Card `text` wraps; it is never truncated or ellipsised (the longest entry runs about 85 characters and must not clip at the grid's minimum column width). Render `text` as a plain string child; this is reviewed engine content and there is no reason for it to ever reach the DOM as markup.

The control is a **boolean toggle per card id**, never a stepper: a tile not in the draft offers `Add`, a tile already in the draft offers `Remove`. That is settled, not provisional — `validateLoadout` has no duplicate-id rule at all, card ids are already per-color variants (`dc_green`, `dc_blue`), and per-card-per-player cooldowns mean a repeated id would buy the player nothing. Because the control only ever offers the valid opposite action for a tile's current state, adding something already present or removing something already absent is not reachable through the UI.
