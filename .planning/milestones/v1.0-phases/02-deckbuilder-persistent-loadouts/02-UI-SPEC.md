# Phase 02 — UI Design Contract

> Visual and interaction contract for the deckbuilder (`/deck` route, HOME-04) and its
> in-lobby embed (DECK-05). Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none |
| Preset | not applicable |
| Component library | none — hand-rolled primitives in `apps/web/components/ui/` |
| Icon library | none — icon *type* (WIRETAP/BRIBE/etc.) is rendered as text, never a glyph library |
| Font | system stack (`ui-sans-serif, system-ui, -apple-system, "Segoe UI", Roboto, sans-serif`) — `apps/web/app/globals.css` |

**No shadcn gate run.** `components.json` does not exist anywhere in the repo, and Phase 1
already shipped a complete, tested, hand-rolled Tailwind v4 token system (`app/globals.css`)
plus a hand-rolled `ui/Button.tsx` primitive under the explicit "clean but plain" baseline
(01-CONTEXT.md D-10: "no theme … deferred to Phase 4"). Introducing shadcn now would fork the
design system mid-project for a phase whose own context explicitly says to reuse, not reinvent,
Phase 1's visual language. This phase adds zero new primitives to `components/ui/` — every new
component (`CardGrid`, `LegalityMeter`, `PresetPicker`, `Deckbuilder`) is built from the existing
Tailwind tokens and the existing `Button` primitive only.

---

## Visual Hierarchy

**Focal point:** the card grid — the large, scrolling primary content area where the actual
build happens (browsing/adding/removing cards). **Secondary:** the legality meter, sticky/pinned
in a right-hand column so it stays visible while the grid scrolls, giving constant reference
without competing for primary visual weight. This mirrors the existing Board (primary) + Orders
(secondary, pinned) split already shipped in `apps/web/app/match/[code]/page.tsx`. Preset
buttons and the primary CTA sit above/adjacent to the legality panel, not inside the scrolling
grid — they are frequent, low-cost actions, not the main task surface.

## Spacing Scale

Declared values (must be multiples of 4) — identical to the Phase 1 scale already in
`01-UI-SPEC.md` and used via Tailwind's default numeric utilities (`gap-N`, `px-N`, `py-N`);
no new `--spacing-*` theme keys, per `globals.css`'s existing comment on why that namespace is
reserved:

| Token | Value | Usage in this phase |
|-------|-------|-------|
| xs | 4px | Gap between an icon-count pip and its neighbor; gap between a sector swatch and its text label |
| sm | 8px | Gap between cards within one icon section's row; gap between the BP bar and its numeric label |
| md | 16px | Default card tile padding; gap between the card grid and the legality panel |
| lg | 24px | Padding around each icon section block; padding inside the sticky legality panel |
| xl | 32px | Gap between the card grid area and the page/lobby chrome around it |
| 2xl | 48px | Not used this phase |
| 3xl | 64px | Not used this phase |

Exceptions: none.

## Typography

Reuses the exact sizes/weights already established and shipped in Phase 1 components
(`OrderComposer.tsx`, `ResultScreen.tsx`, `SeatList.tsx`, `LockedInRow.tsx`) — this phase
introduces no new type sizes or weights. Exactly 4 sizes total, per the UI checker's 4-size
maximum (the researcher's first draft additionally declared 12px/10px micro-badge exceptions;
both are consolidated into the existing Label size below rather than kept as separate sizes).

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 16px (`text-base`) | 400 (`--font-weight-body`) | 1.5 |
| Label | 14px (`text-sm`) | 400, 600 semibold uppercase for badges/pips/emphasized labels | 1.4 |
| Heading | 20px (`text-[20px]`) | 600 (`--font-weight-heading`) | 1.2 |
| Display | 28px (`text-[28px]`) | 600 | 1.2 |

No exceptions. Icon-count pip labels (e.g. "WIRETAP 2/3"), the sector-swatch text label, and
the passive "Consumable"/"Permanent" tag all use the Label size (14px, semibold, uppercase)
rather than a separate micro-badge size.

## Color

Reuses the exact `app/globals.css` `@theme` tokens Phase 1 already defined. This phase adds
zero new UI-chrome colors.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#ffffff` (`--color-surface`) | Page background, `/deck` route background, lobby panel background |
| Secondary (30%) | `#f1f5f9` (`--color-surface-secondary`) | Card tile background, icon-section header background, legality panel background |
| Accent (10%) | `#2563eb` (`--color-accent`) | See reserved-for list below |
| Destructive | `#dc2626` (`--color-destructive`) | Legality-violation states only, see reserved-for list below |
| Border | `#e2e8f0` (`--color-border`) | All card/panel/input borders (existing token, used everywhere) |
| Muted text | `#64748b` | Secondary/helper text (existing, unnamed token, e.g. `SeatList.tsx`'s AI badge) |

**Accent reserved for:**
- The "Save Loadout" primary CTA button fill (lobby context)
- The BP bar fill when the loadout is at-or-under budget (legal)
- The selected/active preset button's border+text (after a preset is loaded, until the next edit)
- The "Loadout legal ✓" positive confirmation line in the legality panel
- Focus rings on any focusable control in the deckbuilder (reuses the existing
  `focus:border-[#2563eb]` pattern from `CreateJoinPanel.tsx`/`CodenameEditor.tsx`)

**Destructive reserved for:**
- The BP bar fill when the loadout is over budget
- An icon-count pip's text/background when that icon's count exceeds 3
- A color-checklist row when fewer than 2 distinct colors are represented
- Every row in the violation-message list (background tint + left border, text stays `#0f172a` for readability — only the border/icon glyph carries the destructive hue, matching `OrderComposer.tsx`'s existing `text-[#dc2626]` rejection-message pattern)
- The violating card's own inline left-border highlight (resolves the "Claude's Discretion" item in `02-CONTEXT.md`: **yes, give the specific violating card(s) their own inline red left-border**, in addition to the meter surfacing the same violation — a player editing a 20+-card grid should not have to cross-reference the meter to find which tile is the problem)
- `SUBMIT_LOADOUT` rejection error text and the localStorage-write-failure error text (see Copywriting Contract)

### Card sector palette (separate namespace — not part of the 60/30/10 UI-chrome budget)

`docs/GAME_DESIGN.md` §6 defines four card **colors** (🟢🔵🔴🟡), which the codebase's `Sector`
type calls `RED | BLUE | GOLD | GREEN`. This is game-domain data, analogous to a categorical
chart palette — it lives alongside, not inside, the UI's accent/destructive semantics.
`apps/web/components/CLAUDE.md`'s existing accessibility rule ("Sector color is never the only
signal — every component encoding a sector also encodes shape or pattern") applies directly:
**every sector swatch is always paired with its 3-4 letter uppercase text label** (RED/BLUE/
GOLD/GREEN), never color alone.

| Sector | Swatch | Paired text label |
|--------|--------|--------------------|
| RED | `#dc2626` | "RED" |
| BLUE | `#2563eb` | "BLUE" |
| GOLD | `#ca8a04` | "GOLD" |
| GREEN | `#16a34a` | "GREEN" |

Note: RED's swatch intentionally reuses the same hex as the UI's destructive color, and BLUE's
swatch intentionally reuses the same hex as the UI's accent color — this is a deliberate,
documented namespace overlap (Cold War red/blue association from the design doc), not an error.
It is safe because sector swatches only ever appear as small pill/chip badges inside a card
tile (never as a full-button fill, never as a page-level state color), and always carry the
mandatory text label above, so the two namespaces are never ambiguous in context.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA (lobby) | "Save Loadout" — disabled until the loadout is legal (D-03); on click, sends `SUBMIT_LOADOUT` and returns to the lobby view. Does not re-ready the player — a separate, existing "Ready" toggle (`SeatList.tsx`) does that. |
| Home-page autosave notice | "Changes save automatically" — small muted-text line near the legality panel; every add/remove persists to `localStorage` immediately regardless of legality (D-01), so there is no separate home-page "Save" button |
| Preset buttons (×4) | "Load Phantom" / "Load Hunter" / "Load Oligarch" / "Load Spider" — ghost-variant buttons, always enabled |
| Destructive confirmation (preset load) | Native `window.confirm()` with body copy: **"Load {ArchetypeName}? This replaces your current loadout."** — resolves the phase's open question of whether overwriting the working draft (D-02) needs a guard: yes, a lightweight native-confirm guard, not a custom modal (no `ui/Dialog` primitive exists yet, and building one is out of this phase's scope) |
| Empty state (violation list, i.e. loadout is legal) | Heading: "Loadout legal" — Body: "10 cards, ≤3 per icon, 2+ colors, ≤26 BP. Ready to save." |
| Error state — SUBMIT_LOADOUT rejected | "Couldn't save your loadout — {server message}. Try again." |
| Error state — localStorage write fails | "Couldn't save changes in this browser. Your edits won't persist after you leave this page." (mirrors `identity.ts`'s treat-storage-as-untrusted posture — this is a warning banner, not a blocking error, since the in-memory draft still works for the current session) |
| In-lobby ready-state notice | On opening the deckbuilder from the lobby: "Editing your loadout — your ready status has been cleared. Ready up again when you're done." (small banner at the top of the embedded deckbuilder, informs the player their `SET_READY {ready:false}` just fired per D-05) |
| Card add/remove control | "Add" (not yet in loadout) → "Remove" (already in loadout) — a boolean toggle per card id, not a stepper. **RESOLVED** (verified against `packages/engine/src/loadout.ts` source directly): `validateLoadout` has no duplicate-id rule at all — it treats `Loadout` as a plain array and only counts per-*icon* totals (`perIcon` Map) and per-*color* presence (`colors` Set) from whatever ids are present, never checking id uniqueness. Card ids are per-color-variant (`dc_green`, `dc_blue`, etc.) — "3× Decoy" in a starter loadout's description means 3 cards sharing the DECOY icon across different colors, not the same id three times. No starter preset repeats an id, and per-card-per-player cooldowns (GAME_DESIGN.md §5) give a duplicate no mechanical benefit. The toggle-per-id control is therefore correct and final, not a planner-confirm item. |

## UI Considerations

Cross-validated against a formal per-element `ui-consideration-probe` run over 6 named surfaces
(card grid, legality panel, preset picker, primary CTA, in-lobby embed, home-page autosave):
30 applicable category checks surfaced, all resolved or explicitly dismissed below (0 left
unaddressed). Applicable state considerations resolved: 18 covered, 2 backstop, 0 unresolved.

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| empty | Violation list | ✅ covered | Zero violations renders the "Loadout legal" positive confirmation (see Copywriting Contract), never a blank panel |
| empty | Card grid | ✅ covered | `ALL_CARDS` is fixed, reviewed engine data (34 cards) — the grid can never have zero cards; dismissed as impossible by data shape, not designed for |
| loading | Card grid, preset buttons, violation list | ✅ covered | All data (`ALL_CARDS`, `STARTER_LOADOUTS`, `validateLoadout()` output) is a synchronous local computation over a static import — no network fetch, so no loading/skeleton state exists for these elements |
| loading | Primary CTA ("Save Loadout") | ✅ covered | Reuses `Button`'s existing `pending` prop (disabled + reduced opacity, no spinner per D-10) while `SUBMIT_LOADOUT` awaits its ack — same pattern as `OrderComposer.tsx`'s submit button |
| error | Card grid, preset buttons, violation list | ✅ covered | Same reasoning as loading — pure local computation, no error state possible; dismissed |
| error | Primary CTA ("Save Loadout") | ✅ covered | `SUBMIT_LOADOUT` rejection renders the defined error copy (see Copywriting Contract); mirrors `OrderComposer.tsx`'s existing `orderStatus.state === 'rejected'` pattern |
| error | Home-page autosave | ✅ covered | localStorage write failure renders the defined warning banner (see Copywriting Contract) |
| populated | Card grid | ✅ covered | Six icon sections in canonical `ICONS` order (AGENT, WIRETAP, BRIBE, DECOY, SAFEHOUSE, STRIKE — `packages/shared/src/enums.ts`, not the informal prose order in `02-CONTEXT.md`), each showing its 4 sector variants, followed by a seventh "Passives" section with all 10 passive cards — matches D-04 and the research's explicit recommendation to use the canonical export |
| populated | Legality panel | ✅ covered | Persistent, always-visible: card count ("X/10"), BP bar with numeric label ("18/26 BP"), 6 icon-count pips ("WIRETAP 2/3" etc.), 4-row color checklist (RED/BLUE/GOLD/GREEN, each with a ✓/✗ text glyph — never a color-only check), violation list below |
| partial | Card grid, legality panel | ✅ covered | Every field on every card and every legality number is always fully computed each render (pure functions over complete data) — there is no partial-data state to design for; dismissed |
| overflow | Card grid | ✅ covered | Main content area scrolls vertically; the legality panel is `sticky`/pinned in a right-hand column (desktop two-column layout, mirroring the existing Board+Orders split in `app/match/[code]/page.tsx`) so it stays visible while the grid scrolls |
| overflow | Violation list | ✅ covered | Stacks vertically inside the legality panel with no cap on count (worst case: all 5 violation codes simultaneously mid-edit); panel scrolls internally if it would overflow the viewport |
| zero-one-many | Icon-count pips (per-icon selected count, 0-3) | ✅ covered | Pip text always shows the numeral regardless of 0/1/2/3 ("STRIKE 0/3" through "STRIKE 3/3") — no icon/pip is hidden at zero |
| zero-one-many | Color checklist (0-4 distinct colors present) | ✅ covered | All 4 rows always render; rows for absent colors show "✗" and dim/muted text, not removed from the list |
| loading / error / long-text | Preset picker (4 buttons) | ✅ dismissed | `STARTER_LOADOUTS` is fixed local data with no network call — no loading/error state possible; button labels are 4 fixed short archetype names ("Load Phantom" etc.), never long text |
| empty / populated | In-lobby deckbuilder embed | ✅ covered | Same card grid + legality panel populated/empty behavior as the home-page surface (identical component, D-05); the embed's *distinguishing* state is the ready-clear banner below |
| error | In-lobby deckbuilder embed | ✅ covered | Same `SUBMIT_LOADOUT`-rejected copy as the home-page primary CTA (see Copywriting Contract) — the lobby embed reuses the CTA, not a separate save path |
| populated (banner) | In-lobby ready-state notice | ✅ covered | Always shown immediately on opening the lobby embed, before any card edits — "Editing your loadout — your ready status has been cleared…" (see Copywriting Contract); never conditionally hidden |
| long-text | Card ability text (`Card.text`, e.g. "Claim the informant on your node. In a GOLD sector, +2 Intel immediately.") | 🧪 backstop | Card tiles wrap text normally (no truncation/ellipsis) — verified by a held-out visual check that the longest `Card.text` in `ALL_CARDS` (currently the GOLD Bribe card, ~85 chars) does not clip or overflow its tile at the grid's minimum column width |
| long-text | Violation message text (`LoadoutViolation.message`, engine-authored) | ✅ covered | Wraps normally inside the violation list row; no character limit imposed by the UI since the engine already produces short, fixed-shape messages |
| zero-one-many | Card add/remove duplicate-id interaction | ✅ covered | Resolved by direct source read of `packages/engine/src/loadout.ts`: no duplicate-id rule exists; ids are already per-color-variant so a duplicate is semantically meaningless. Toggle-per-id control confirmed final. |
