> codes, the host controls the room, everyone can talk, and one person dropping does not kill the

**This plan's slice:** a player with no join code can see a real lobby someone else opened and join
it with one click.

<objective>
Deliver HOME-03 end to end: a second PartyKit party (`directory`) acting as a singleton registry
that every match room pushes its public lobby metadata into, and a live home-page Open Lobbies list
reading it over a WebSocket.

This is the phase **tracer**. It is the only architecturally novel work in Phase 3 — a second
Durable Object class, a cross-party `fetch()` write path, and a second client socket — and every
later plan in this phase adds handlers, seat fields, and UI on top of an architecture this plan
must prove first. It is production-quality, not a prototype: the wire schemas, the registry
semantics, and the join path it establishes are the ones Phase 3 ships.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → directory party (WebSocket) | Read-only subscription from an unauthenticated stranger; anyone on the internet can open it |
| match room → directory party (cross-party HTTP fetch) | Still an untrusted-input boundary even though the caller is this project's own code — a bug in the match room can send malformed data |
| directory party → every connected browser (DIRECTORY_STATE fan-out) | One identical payload reaches players who are not in any of the listed rooms |
| browser → match room (JOIN from a list row) | The one-click join is an ordinary untrusted JOIN, indistinguishable from a typed code |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-01 | Information Disclosure | `directoryEntrySchema` / `syncDirectory` payload | high | mitigate | The entry schema is built with `z.strictObject` and holds exactly `code`, `seatsFilled`, `seatsTotal`, `hostCodename`. Any future field added to the outbound payload without a matching schema change is a parse failure at the directory, not a silent leak. Enforces prohibition P-3-01. Test: the unknown-key rejection case in Task 1's acceptance criteria. |
| T-03-02 | Denial of Service | `LobbyDirectory.onRequest` | medium | mitigate | Method-gated to POST (405 otherwise); body `JSON.parse` wrapped in try/catch (400); `directoryCommandSchema.safeParse` gates every mutation (400). No path stores an unvalidated value. Test: Task 3's four input-hardening cases, each paired with an unchanged-state assertion. |
| T-03-03 | Spoofing | one-click Join from a directory row | low | accept | A directory row is a hint, not an authorization. The click issues the same `JOIN` the code-entry form issues, and `handleJoin` independently answers `UNKNOWN_CODE` for a code that no longer names a room and `ROOM_FULL` when no `OPEN` seat remains (which is always true once `fillEmptySeatsWithBots` has run at match start). A forged or stale row can therefore only produce an error reply, never an unauthorized seat. |
| T-03-04 | Tampering | stale directory entry after a failed alarm-context REMOVE | low | accept | 03-RESEARCH.md Open Question 2 records the abandoned-lobby stale-entry gap as an explicitly accepted, out-of-scope-this-phase gap (no TTL/heartbeat). The exposure is bounded: Task 2's `SUBMIT_ORDER` self-heal removes the entry on the first inbound message after match start, and an unreachable stale row degrades to T-03-03's error reply. |
| T-03-05 | Repudiation | directory writes carry no origin attestation | low | accept | Cross-party `fetch()` inside a single PartyKit project is not externally reachable; the directory party is not exposed as a public write endpoint to browsers (browsers only open the read-only WebSocket). No attestation mechanism is warranted at ASVS L1 for a no-accounts lobby list. |
</threat_model>
